# Spec-Driven Development

## Key Points

In an agent-first workflow, specifications become the primary programming surface. A well-written spec is itself executable — agents can read it, implement it, and validate the implementation. Code becomes a disposable build artifact, compiled from the spec by the LLM as a "fuzzy compiler."

## Spec as the System

The Symphony project demonstrates this pattern: the entire system is defined in a single `SPEC.md` file. The spec describes:

- The problem statement and goals/non-goals
- The domain model (entities, fields, normalization rules)
- The state machine and transition triggers
- Configuration specifications with precedence and defaults
- Integration contracts for external systems
- Error handling and observability requirements

The spec is language-agnostic and can be implemented by any agent in any language.

## Building the Spec with the Agent

The workflow for spec-driven development:

1. **Define the problem** — Write a spec describing what needs to be built and why
2. **Point the agent at the spec** — The agent reads the spec and generates an implementation
3. **Validate via implementation** — Have the agent implement the spec in multiple languages to find ambiguities
4. **Iterate** — Refine the spec based on implementation failures
5. **Use the system to build the system** — Once basic functionality exists, use it to develop itself

## Validating Specs Through Multi-Language Implementation

To identify ambiguities in a spec, have agents implement it in several languages (TypeScript, Go, Rust, Java, Python). If a spec succeeds in every language, it is sufficiently clear and complete. This is a form of "dogfooding" the spec itself.

## WORKFLOW.md as the Runtime Contract

In orchestration systems like Symphony, `WORKFLOW.md` serves as the repository-owned contract that defines:

- YAML front matter with runtime configuration (polling, concurrency, hooks)
- Markdown body as the prompt template for per-issue agent tasks
- Dynamic reload semantics — changes apply without restart

This pattern generalizes: any agent-first repository can define its development workflow in a version-controlled file that agents are required to follow.

## Code as a Disposable Build Artifact

In this paradigm, code is like compiled x86 instructions — generated by the LLM "compiler" from the spec "source code." The value is in the spec, the constraints, and the guardrails that got you there, not in the code itself. This means:

- Refactoring is free — agents can migrate the entire codebase to match new specs
- Migrations always complete — fire many agents to finish migrations that would hang open for months
- The spec is the durable artifact; the code is transient
