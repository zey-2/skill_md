A Lesson on the Next Era of Software

Software 3.0

From hand-coded rules to orchestrated intent — how we went from writing logic to describing outcomes and letting AI agents figure out the rest.

Workshop / Lecture 2026
01 / 14

Welcome everyone. Today I want to talk about something that is quietly reshaping how we build software — and it's not a new framework or language. It's a fundamental shift in the paradigm of what software even is.

Most of us grew up in the world of Software 1.0: we write code, the code does exactly what we tell it. Then came 2.0: we stopped writing logic and started training models on data. Now we're entering Software 3.0 — where the "code" is natural language intent, and the runtime is a fleet of AI agents that plan, use tools, and self-correct.

This isn't theoretical. It's happening right now in production systems. By the end of this session, you'll understand what Software 3.0 is, why it matters, and how to think about engineering in this new world.

01

The Evolution

Three paradigms. Three ways of telling computers what to do.

02 / 14

Let's start with some history. Understanding where we came from is essential to understanding where we're going.

Software has gone through three distinct paradigms — each one redefining the relationship between human intent and machine execution. This isn't about version numbers. It's about who writes the logic.

In 1.0, humans write every rule. In 2.0, humans curate data and machines learn the rules. In 3.0, humans describe intent and machines orchestrate the solution.

Each step moves more agency to the machine. Let's look at each one.

Software 1.0

Hand-Coded Logic

  • Humans write explicit rules — if-this-then-that, algorithms, control flow
  • Deterministic and debuggable — same input always produces same output
  • Brittle on ambiguous problems — image recognition, natural language, edge cases
  • Scaling requires more engineers — every new feature means more code to write and maintain
  • The programmer is the bottleneck — complexity grows faster than our ability to manage it
// Software 1.0: explicit rules
function classifyEmail(email) {
  if (email.subject.includes("free"))
    return "spam";
  if (email.sender.isTrusted())
    return "inbox";
  // ... hundreds more rules
}
03 / 14

Software 1.0 is what most of us learned in school. You write functions, conditionals, loops. The computer follows your instructions exactly. This works brilliantly for well-defined problems: sorting, arithmetic, business rules with clear boundaries.

But it falls apart on ambiguous, fuzzy problems. How do you write an if-statement for "does this email look like spam?" or "is this image a cat?" You end up with hundreds of hand-crafted heuristics that never quite cover all the edge cases.

The fundamental constraint here is human bandwidth. Every new behavior requires a human to understand it, encode it, test it, and maintain it. As problems get more complex, the codebase grows faster than our ability to manage it. This is the complexity wall.

Look at the code example — a simple email classifier. In the real world, this function would have hundreds of conditions, and still miss things. That's the 1.0 ceiling.

Software 2.0

Neural Networks & Weights

  • Humans curate data, machines learn patterns — the "code" becomes millions of floating-point weights
  • Excels at perception tasks — vision, speech, pattern recognition at superhuman accuracy
  • Opaque and hard to control — you can't debug a 175-billion-parameter matrix
  • Requires massive datasets and compute — the new bottleneck is data quality and GPU hours
  • Coined by Andrej Karpathy — "the best performing models are not coded, they are trained"
// Software 2.0: learn from data
model = Transformer(
  layers=96,
  params=1.8T,
  data=load_dataset("the-internet")
)
model.train()
// weights now encode "knowledge"
// no one knows exactly how
04 / 14

Then came Software 2.0. Instead of writing rules, we started curating datasets and letting neural networks figure out the patterns themselves. Andrej Karpathy coined the term in 2017, and it was prophetic.

The "code" in 2.0 isn't Python or C++ — it's billions of floating-point numbers inside a neural network. You don't write this code. You train it. You feed it data, compute gradients, and hope it converges.

For perception tasks — image recognition, speech-to-text, translation — 2.0 absolutely crushed 1.0. Superhuman accuracy. But there's a catch: you can't control it precisely. You can't ask a 175-billion-parameter model "why did you output that?" It's a black box.

And the bottleneck shifted from human engineers to data quality, compute resources, and GPU clusters. Training a modern model costs millions. This paradigm is powerful but expensive and opaque.

2.0 is incredible at recognizing patterns. But it struggles at following instructions precisely. That gap is what 3.0 fills.

Software 3.0

Intent & Orchestration

  • Humans describe intent in natural language — the system figures out the implementation
  • Agents plan, use tools, and self-correct — not just pattern-matching, but reasoning loops
  • Skills replace functions — behavior defined by prompts, examples, and constraints
  • Context shapes behavior at runtime — retrieved knowledge, conversation history, tool outputs
  • The engineer becomes an orchestrator — designing systems, not writing every line
// Software 3.0: describe intent
skill: "classify incoming emails"
tools: [email_api, calendar, crm]
constraints: [
  "flag urgent for boss",
  "batch newsletters to Friday",
  "learn from my corrections"
]
// agent handles the rest
05 / 14

Software 3.0 is where we are now. The shift is profound: instead of coding logic or training weights, we describe what we want in natural language and the system figures out how to do it.

The key innovation is agentic reasoning. These aren't just autocomplete models. They plan multi-step workflows, call APIs, read files, write code, test it, fix their own mistakes, and loop until the task is done. This is fundamentally different from both 1.0 and 2.0.

In 3.0, the basic unit isn't a function — it's a skill: a natural language description of behavior, plus examples, plus constraints. You compose skills together like LEGO bricks to build complex systems.

And critically, context is the new code. The behavior of a 3.0 system is dynamically shaped by what it knows at runtime — retrieved documents, conversation history, the output of tool calls. The "program" is assembled on the fly.

The engineer's role shifts from writing code to designing systems — choosing which agents to use, what tools to give them, how to evaluate their output, and when to step in.

06 / 14

This slide is the core mental model for everything that follows. Read it left to right and notice the progression of agency.

In 1.0, the developer is the author — every conditional, every loop, every edge case handler. The machine is a faithful executor.

In 2.0, the engineer is a curator — you pick the right dataset, the right architecture, the right loss function. The machine discovers patterns you could never code by hand.

In 3.0, the human is an orchestrator — you define what needs to happen, what tools are available, what quality bar to meet, and when to escalate to a human. The machine plans, acts, and self-corrects.

Notice the debugging model changes too: stack trace -> accuracy metrics -> reasoning traces. And the scaling factor: team size -> compute -> skill composition. These aren't incremental improvements. They're different worlds.

02

Core Concepts

The building blocks of Software 3.0 systems.

07 / 14

Now let's dive into the core concepts that make Software 3.0 work. These are the ideas you need to internalize to design systems in this new paradigm.

I'll cover four concepts: skills over code, agentic workflows, composable AI systems, and context as the new code. Each one is a shift in how we think about building software.

These aren't abstract — they're all being used in production systems today. By the end, you'll see how they fit together.

Concept 01

Skills Over Code

01

Natural Language Specs

Behavior is defined by prompts, examples, and constraints — not source code. The LLM interprets intent and generates the execution plan.

02

Examples as Tests

Few-shot examples replace unit tests. Show the model what good output looks like, and it generalizes to new inputs.

03

Iterative Refinement

Skills improve through feedback loops: evaluate output, adjust the prompt, re-test. No recompilation needed.

// A skill is a natural-language contract
name: "summarize-meeting"
description: "Take transcript and produce"
             "a 5-bullet summary with"
             "action items and owners"
examples: [
  { input: "[transcript...]",
    output: "[summary...]" }
]
08 / 14

The first core concept: skills replace functions as the basic unit of behavior. A skill is a natural language description of what should happen, paired with examples of good output.

Think of it like a function signature, but in English instead of type annotations. The name tells you what it does, the description provides context, and the examples serve as test cases.

The biggest difference from traditional code: skills are iterative and non-deterministic. You don't "debug" a skill — you evaluate its output, tweak the prompt, add better examples, and try again. The development loop is more like training than compiling.

This is why evaluation-driven development becomes the new testing. Instead of asserting that a function returns a specific value, you score the output on quality dimensions: accuracy, completeness, tone, format compliance.

The skill in the code example — "summarize-meeting" — would be impossible to write deterministically in 1.0. You'd need NLP pipelines, entity extraction, template matching. In 3.0, you describe what you want and the model does it.

Concept 02

Agentic Workflows

  • Plan — the agent breaks down a goal into steps before acting
  • Act — executes steps using tools: APIs, code execution, file I/O, web search
  • Observe — reads tool output, checks for errors, validates results
  • Reflect — self-evaluates: "did this work? should I try a different approach?"
  • Iterate — loops until the task is complete or escalates to a human
// The ReAct loop
THOUGHT: I need to find the
  user's last order first
ACTION: query_db(
  "SELECT * FROM orders
   WHERE user_id=42
   ORDER BY date DESC LIMIT 1"
)
OBSERVATION: {order_id: 7891}
THOUGHT: Now I can get details
ACTION: fetch_order(7891)
OBSERVATION: {...}
FINAL ANSWER: The order is...
09 / 14

The second concept is agentic workflows — the loop that makes 3.0 systems powerful. This is the ReAct pattern: Reason and Act.

Unlike a 2.0 model that just generates text, an agent thinks before it acts. It writes out its reasoning as "THOUGHT" tokens, decides what tool to call, reads the result, and decides what to do next.

Look at the example on the right. This is a real interaction trace from an agent handling a customer query. Notice how it plans sequentially: first find the order, then fetch details, then compose the answer. Each step is informed by the previous observation.

The key insight: agents can self-correct. If the database query fails, the agent can try a different query. If the result doesn't make sense, it can backtrack. This is fundamentally different from 1.0 code, where an unhandled exception crashes the program.

This loop — plan, act, observe, reflect, iterate — is the core execution model of Software 3.0. Everything else builds on this.

Concept 03

Composable AI Systems

Not one monolithic model. Multiple specialized agents and tools orchestrated together.

A

Researcher

Searches, reads, and synthesizes information from multiple sources.

W

Writer

Drafts content with specific tone, format, and audience constraints.

R

Reviewer

Fact-checks, critiques, and scores output against quality criteria.

E

Executor

Takes approved output and deploys, publishes, or integrates it.

Researcher → Writer → Reviewer → (revise loop) → Executor

10 / 14

Third concept: don't use one model for everything. The best 3.0 systems compose multiple specialized agents, each optimized for a specific role.

Think of it like a newsroom. A researcher gathers facts. A writer drafts the article. An editor reviews and fact-checks. A publisher pushes it live. Each role has different skills, different tools, different quality criteria.

The flow at the bottom shows the pipeline: the researcher finds information, the writer drafts content, the reviewer scores it. If the score is below threshold, it goes back for revision. Only approved output reaches the executor.

This composition pattern is powerful because each agent can use a different model. The researcher might need a model with strong web search. The writer might need one with great prose. The reviewer might need one fine-tuned for fact-checking. You pick the best tool for each job.

And critically, failure is localized. If the reviewer catches a problem, it doesn't crash the system — it triggers a revision loop. The system degrades gracefully instead of catastrophically.

Concept 04

Context Is the New Code

In 1.0, behavior was hardcoded. In 2.0, it was baked into weights. In 3.0, behavior is assembled at runtime from whatever context the agent has access to.

  • Retrieved knowledge — RAG pulls relevant documents into the prompt
  • Conversation history — prior turns shape what the agent knows and remembers
  • Tool outputs — API responses, file contents, search results become part of the "program"
  • System prompts — the standing instructions that define role, constraints, and style
// The "program" at runtime:
[system prompt]
  "You are a technical writer...
   follow style guide v3..."
[retrieved docs]
  API spec for /users endpoint
  Brand voice guidelines
[conversation history]
  User: "explain OAuth simply"
[tool output]
  {user_schema: {id, email...}}
// = the complete "source code"
11 / 14

This is perhaps the most important concept: context is the new code. In Software 3.0, the "program" doesn't exist as a static file on disk. It's assembled at runtime from whatever the agent has access to in that moment.

Look at the code example on the right. That entire prompt — system instructions, retrieved documents, conversation history, tool outputs — that's the source code for a 3.0 system. It's different every time the agent runs, because the context is different.

This means the engineering work shifts from writing logic to managing context. What documents does the agent have access to? What's in the system prompt? What tools can it call? How much conversation history is included?

Retrieval-Augmented Generation (RAG) is the key technique here: instead of baking knowledge into model weights, you retrieve the relevant facts at runtime and inject them into the prompt. This means you can update the agent's "knowledge" by updating the documents, not retraining the model.

This is why context engineering — the art of designing what goes into the prompt and when — is becoming the most valuable skill in the 3.0 toolkit.

03

Engineering Shifts

How the practice of software engineering changes in the 3.0 era.

12 / 14

So far we've covered the what. Now let's talk about the how — how engineering practice changes when you're building with agents instead of writing functions.

Two big shifts: evaluation-driven development replaces unit testing, and human-in-the-loop design replaces fully automated pipelines.

These aren't optional. If you try to apply 1.0 engineering practices to 3.0 systems, you will fail. The tools and mental models need to evolve.

Shift 01

Evaluation-Driven Development

  • Non-deterministic output means unit tests don't work — you can't assert exact string matches
  • Evaluate with scored rubrics — accuracy, completeness, format compliance, tone
  • Golden datasets over assertions — run hundreds of inputs through the skill and score the outputs
  • Regression detection via embedding similarity — catch when output quality drifts
  • Continuous evaluation in CI/CD — every prompt change runs the eval suite before deploy
// Eval-driven development
eval_suite: [
  { input: "explain async",
    criteria: {
      accuracy:   >= 0.9,
      simplicity: >= 0.8,
      format:     "bullet list",
      max_length: 200 words
    }
  },
  // ... 200 more test cases
]
// Score: 94/100 -> deploy
13 / 14

This is the biggest practical shift for engineers moving to 3.0. You can't write unit tests for non-deterministic output. Asserting that a function returns exactly "hello world" doesn't work when the model might say "hi there" or "greetings" — both equally correct.

Instead, you build evaluation suites with scored rubrics. Each test case has input, expected criteria, and a scoring threshold. You might use another LLM as a judge, or embedding similarity, or specific factual assertions that must be true in the output.

The eval suite becomes your quality gate. Before any prompt change goes to production, it runs through hundreds of test cases. If the aggregate score drops, the change is rejected. This is the 3.0 equivalent of a test suite blocking a bad merge.

And here's the twist: your eval suite IS your product quality bar. The better your evals, the better your system. Investing in eval quality — more cases, better rubrics, harder edge cases — is the highest-leverage work you can do in 3.0 engineering.

Companies building serious 3.0 systems spend more time on their eval infrastructure than on their prompts. That tells you everything about where the leverage is.

Takeaway

The Code Is the Prompt

Software 3.0 isn't about replacing engineers. It's about elevating them — from writing every line to designing systems that write themselves. The skill is no longer syntax. It's specification.

Build skills, not functions. Describe intent, provide examples, iterate on output.

Design evals, not tests. Score quality with rubrics, not exact matches. Your eval suite is your product.

Orchestrate, don't code. Compose agents, manage context, and keep humans in the loop.

Third: orchestrate, don't code. The value is in how you compose agents, manage context, and decide when humans stay in the loop.

The code is the prompt. The compiler is the agent. The runtime is context. Welcome to Software 3.0.
